> [!TIP]
> 1. **Event Notification**: Service phát ra sự kiện ngắn gọn chỉ báo hiệu trạng thái thay đổi, service nhận sẽ tự query dữ liệu chi tiết nếu cần.
> 2. **Event-Carried State Transfer**: Sự kiện chứa sẵn toàn bộ payload dữ liệu để service nhận update cache nội bộ mà không cần gọi lại service gốc.
> 3. **Event Sourcing**: Lưu trữ lịch sử thay đổi của state dưới dạng chuỗi sự kiện không thể thay đổi (append-only log), phù hợp cho hệ thống kế toán / ví điện tử.

## 1. Khi nào nên dùng Event-Driven Architecture (EDA)?

Khi hệ thống có số lượng service phụ thuộc lẫn nhau tăng lên, các lời gọi API HTTP đồng bộ (Synchronous HTTP calls) sẽ gây nên hiện tượng Cascading Latency (độ trễ dây chuyền).

EDA giải quyết vấn đề này bằng cách cho phép producer và consumer hoàn toàn độc lập về mặt thời gian (temporal decoupling).

---

## 2. Event-Carried State Transfer trong thực tế

Thay vì chỉ gửi `{ "orderId": 123 }`, event sẽ mang theo toàn bộ dữ liệu đơn hàng cần thiết:

```json
{
  "eventId": "evt_998877",
  "eventType": "ORDER_CREATED",
  "timestamp": "2026-06-25T10:30:00Z",
  "payload": {
    "orderId": "123",
    "userId": "usr_456",
    "totalAmount": 1500000,
    "items": [
      { "productId": "prod_1", "quantity": 2 }
    ]
  }
}
```

---

## 3. Lựa chọn Message Broker: Redis vs Kafka vs RabbitMQ

- **Redis Pub/Sub & Streams**: Phù hợp khi cần độ trễ thấp và triển khai đơn giản, ví dụ notification hoặc chat. Pub/Sub không lưu lại tin nhắn, nên dùng Streams nếu không được phép mất event.
- **RabbitMQ**: Hỗ trợ định tuyến tin nhắn linh hoạt (Topic / Direct / Fanout Exchange) và work queue.
- **Apache Kafka**: Phù hợp cho luồng dữ liệu lớn (stream processing) và khi cần lưu log sự kiện lâu dài để đọc lại.
